Intake & Validation Layer (Synchronous) — Steps 1A · 1B · 1C  ·  No SQS — Caller Expects Immediate Response
Phase 1 Architecture Decision: This layer is intentionally synchronous. The upstream caller expects an immediate response containing caseId, policyVersion and presigned upload URLs. Introducing SQS here would break request/response semantics, require polling or callbacks, and add unnecessary latency. Failure handling is simple — API Gateway returns 5XX and the caller retries. No buffering is needed.

Recovery Architecture Principles
All compute components are stateless
All workflow state stored externally (Aurora + DynamoDB)
Every step is idempotent — safe to retry
No step relies on in-memory session state
Workflow progress is checkpointed at each stage
All asynchronous processing is durable via SQS
DLQ ensures zero silent message loss
EventBridge 30-day archive enables full replay
Failure Scenario — Extraction Lambda Crashes Mid-Processing
1. Step Functions sends message to extraction-queue
2. Lambda extracts 2 of 3 documents successfully
3. Writes results for 2 docs to Aurora
4. Lambda crashes — DynamoDB status NOT updated
5. Message becomes visible again after visibility timeout
6. Lambda retries — checks Aurora for completed work
7. Skips already-extracted 2 documents (idempotent)
8. Processes remaining document
9. Updates DynamoDB → DATA_EXTRACTED
✓ No duplication · ✓ No data loss · ✓ No restart from beginning
Infrastructure Failure Coverage
FailureRecovery Mechanism

State Management — DynamoDB case_runtime_state Checkpointing
Each workflow stage updates DynamoDB status only after successful completion. If failure occurs mid-stage, status does not advance. Step Functions retries. Lambda reads Aurora to determine already-completed work and resumes from checkpoint.
